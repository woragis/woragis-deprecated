# LinkedIn Guide - Technical Content Strategy

## Platform Overview
LinkedIn is the professional network for technical content. Focus on architecture, technical decisions, and professional insights.

## Positioning

### Personal Brand
- **Role**: Senior Backend Engineer / Software Architect
- **Expertise**: Microservices, Distributed Systems, Go, Python
- **Value Proposition**: Building scalable backend systems, sharing real-world experience
- **Tone**: Professional, technical, but accessible

### Content Focus
- Architecture decisions and patterns
- Technical deep dives
- Lessons learned from real projects
- Industry insights
- Career and professional development

## Content Depth & Technical Level

### Depth Level: **Medium-High**
- **Length**: 500-800 words per post
- **Technical Detail**: Detailed but accessible
- **Code Examples**: Yes, with explanations
- **Diagrams**: Architecture diagrams, flowcharts
- **Target Audience**: Mid-to-senior engineers, architects, tech leads

### Technical Content Guidelines
- Explain technical concepts clearly
- Include code snippets (syntax-highlighted)
- Use diagrams for complex topics
- Provide context and trade-offs
- Share real-world examples

## Visual Identity

### Image Strategy
- **Primary**: Architecture diagrams, flowcharts
- **Secondary**: Code snippets (syntax-highlighted)
- **Style**: Clean, professional, technical
- **Tools**: Mermaid, Draw.io, Carbon (for code)

### Image Quantity
- **Per Post**: 1-2 images (diagram + code snippet)
- **Format**: PNG/JPG, high resolution
- **Size**: 1200x627px (LinkedIn recommended)
- **Alt Text**: Always include for accessibility

### Visual Elements
- Consistent color scheme
- Code syntax highlighting (GitHub-style)
- Professional diagrams
- Clean typography

## Posting Strategy

### Frequency
- **Posts per Week**: 1-2 (from your 5/week schedule)
- **Best Days**: Tuesday, Wednesday, Thursday
- **Best Times**: 8-10 AM, 12-1 PM (local time)

### Post Types

#### 1. Architecture Posts (Monday)
- Microservices architecture
- System design patterns
- Technology choices
- **Format**: Long-form post with diagram
- **Length**: 600-800 words

#### 2. Technical Decision Posts (Tuesday)
- ADR explanations
- Why we chose X over Y
- Trade-offs and consequences
- **Format**: Long-form post with flowchart
- **Length**: 500-700 words

#### 3. Implementation Deep Dives (Wednesday)
- How we implemented X
- Code examples
- Challenges and solutions
- **Format**: Long-form post with code snippets
- **Length**: 600-800 words

#### 4. Lessons Learned (Thursday)
- What I learned building X
- Mistakes and improvements
- Best practices
- **Format**: Long-form post with insights
- **Length**: 500-700 words

#### 5. Cross-Cutting/Advanced (Friday)
- Observability, metrics, tracing
- Advanced patterns
- Future improvements
- **Format**: Long-form post with diagrams
- **Length**: 600-800 words

## Post Structure

### Standard Template
1. **Hook** (1-2 sentences): Problem or interesting insight
2. **Context** (2-3 sentences): Background and why it matters
3. **Main Content** (3-5 paragraphs): Technical explanation
4. **Key Takeaways** (bullet points): 3-5 key points
5. **Call to Action** (1 sentence): Question or discussion prompt

### Example Structure
```
🚀 Building a resilient message queue system

Problem: Need reliable message queue that doesn't fail when RabbitMQ is down.

Solution: RabbitMQ + Redis fallback pattern.

[Technical explanation with code examples and diagram]

Key takeaways:
✅ High availability (99.9%+)
✅ Graceful degradation
✅ No single point of failure
✅ Workers continue processing

What's your approach to message queue resilience?

#BackendEngineering #Microservices #RabbitMQ #SystemDesign
```

### Secondary Hashtags (3-5 per post)

### Best Practices
- Mix popular and niche hashtags
- Use 5-8 hashtags total
- Include location if relevant (#BrazilTech)

- Share additional insights

### Networking
- Connect with other engineers

- Join relevant groups

### Content Amplification
- Share in relevant LinkedIn groups
- Tag relevant people (sparingly)
- Cross-post to Twitter (with link)
- Include in newsletter (if you have one)

## Do's and Don'ts

### Do's
✅ Share real-world examples
✅ Include code and diagrams
✅ Explain trade-offs
✅ Engage with comments
✅ Post consistently
✅ Use professional language
✅ Provide value

### Don'ts
❌ Over-promote yourself
❌ Use clickbait
❌ Post without value
❌ Ignore comments
❌ Use too many hashtags
❌ Post inconsistently
❌ Share unverified information
